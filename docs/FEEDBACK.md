# 实机体验反馈与整改方案

来源：2026-08-18 首次自行安装 + 真实账号试用后的反馈。
本文只记「反馈 → 结论 → 方案 → 状态」，设计细节最终会回流到 `PRD.md` / `TECH_SPEC.md`。

状态图例：✅ 已完成 · 🚧 进行中 · 📋 待做

---

## 一、配置

### 1. 默认 Base URL 应为生产环境 ✅
默认值是 `read-web-test.puzle.com.cn`（测试环境）。已改为 `https://read-web.puzle.com.cn`。
`read-web` / `read` / `puzle.com.cn` 三个域名实测指向同一后端，取仓库测试中标注为生产的那个。

### 2. 同步文件夹可自定义 ✅
**该设置本来就有**（设置 → 根目录，默认 `PuzleRead`），但是个裸文本框，容易被忽略、也容易打错路径。
已改为：输入时自动补全 Vault 内已有文件夹，并对首尾斜杠做归一化。

### 3. 同步的文章设为只读 ✅
Obsidian 没有「文件只读」API。能做到的最接近方案是**打开即阅读模式**：
打开根目录下（或带 `puzle_type` frontmatter）的笔记时自动切到阅读视图，
用户仍可 Cmd/Ctrl+E 切回编辑 —— managed 区之外自由记笔记本来就是既定设计。
新增设置项「以阅读模式打开同步内容」，默认开。

## 二、高亮与批注

### 4. 高亮不该只靠 wiki link 跳转，要有侧边栏 ✅
现状：高亮是 `Highlights/*.md`，正文里靠 `==高亮==` + `💬` 角标 + 双链关联，必须点进去才能看内容。

方案：新增右边栏「批注」视图（`ItemView`），跟随当前打开的文章：
- 列出该文章全部高亮（按正文顺序）、每条高亮下挂它的评论、以及文章级评论；
- 点侧栏条目 → 正文滚动并闪烁定位；点正文角标 → 侧栏对应条目高亮；
- `Highlights/*.md` 与 Bases 视图保留（数据与检索能力不变），侧边栏是新的主交互面。

### 5. 划词创建高亮 / 评论 ✅
现状：完全没有创建入口，插件是只读同步。后端其实有
`POST /api/v1/reading/highlights`、`POST /api/v1/reading/comments`。

难点：高亮的 `location_data.start_index/end_index` 是**「Web 端渲染后正文纯文本的字符偏移」**，
而 Obsidian 这边是 HTML→Markdown 转换后的结果，偏移对不上。

方案（反向映射，不需要后端改动）：
1. 正文 HTML 缓存到 `.obsidian/plugins/puzle-read/cache/article-<reading_id>.html`，
   纯文本 PT 按当前口径就地推导（缓存 HTML 而不是 PT：换口径能重算，不必再请求一次）。
2. **正确性自证**：口径（是否折叠空白、块间是否换行）文档没写死，所以实现了 4 种候选口径
   （`raw` / `blockNewline` / `collapseNewline` / `collapseDoubleNewline`），
   设置里的「自动校准」拿账号已有高亮当标准答案，逐个口径校验 `PT.slice(start,end) === content`
   的命中率，选中率最高的那个并记进设置。**首次使用需要跑一次校准**。
3. Markdown 选区 → PT 偏移（`annotations/locate.ts`）：两边都归一化成「有效字符序列」
   （只留汉字/字母/数字，Markdown 标记、空白、标点、URL 全部丢掉），
   选区在 MD 里是第 k 次出现，就取 PT 里的第 k 次出现 —— 重复段落天然消歧，
   不需要做全文对齐。PT 侧按 Unicode code point 计数，与后端口径一致。
   回传的 `content` 直接取 PT 切片而不是用户选中的原文，保证 content 与 start/end 自洽。
4. 交互：正文选中文字后右键菜单 /「创建高亮」「写评论」；写回成功后就地更新侧栏与正文标记。

### 6. 文章级（全局）评论要有展示与创建入口 ✅
澄清：**展示是有的** —— 文章笔记 managed 区里的 `## 想法` 段就是文章级评论，
只是账号里没有这类数据时整段不出现，所以看起来像缺失。
待补的是**创建入口**：侧边栏底部一个输入框，直接发文章级评论。

## 三、对话

### 7. 聊天没有和文章挂钩 ✅
后端本来就支持：`ReadingItem.chat_id` 是该文章关联的会话；
WebSocket `chat_completion` 支持 `context: {type:'reading', params:{reading_id, selected_text}}`。
插件一直没用上，所以右边栏聊天是「悬空」的通用对话。

方案：
- 文章视图提供「与本文对话」入口；已有 `chat_id` 就直接继续那个会话，**不允许对同一篇文章再开新会话**；
- 首次对话时带 `context.reading_id` 发起，拿到 ack 的 `chat_id` 后落到该文章的状态里；
- 划词后可「就这段提问」，带 `selected_text`。

### 8 / 9. Chats 的形态：先改插件内视图，后又改回 Markdown ✅
第一轮决策是「去掉 `Chats/*.md`，对话只活在插件里」：左边栏会话列表 + 主区域聊天页 + 右边栏快捷入口。

**第二轮（试用后推翻，本次落地）**：为了看一段对话要多开一个左边栏，代价大于收益。定为：
- **删掉左边栏会话列表与主区域聊天页**，聊天只留右边栏面板一个入口（会话切换靠面板顶部下拉）；
- 对话**重新以 Markdown 呈现**，`Chats/{标题} (c{chat_id}).md` 恢复同步（`ChatSyncer` 回来了）；
- 更进一步：**不必等同步** —— 聊天时每说完一轮就把整段会话重渲染写回那个 md，
  面板顶部的 📄 直接在主区域打开它。

与同步的配合（`sync/chat-notes.ts`）：
- 写回和 `ChatSyncer` 共用 `syncState.chats` 的 `path / turnCount / managedHash` 一套记账 ——
  下次增量同步看到回合数一致直接跳过，`onEditedManaged='skip'` 也不会把插件自己的写回误判成用户编辑；
- 回合数口径**宁少勿多**（少算最多重写一遍，多算会让同步误判「没变」而漏掉），
  所以本地发出的用户消息在 `turn_end` 时补上 `turn_id` 再计数；
- 流式过程中只标记 busy 不写盘，同步遇到 busy 的会话直接跳过 —— 否则服务端还没落库的最后一轮会被旧历史盖掉。

顺带修（第一轮就做了，保留）：会话列表要遍历 `/api/v1/reading/items` **全部分页**再筛 `resource_type === 'chat'`，
账号内容多时长时间空白，看起来像「没有列表」。改为边翻页边增量渲染 + 结果缓存。

## 二轮补充：右键菜单与「不必等同步」

### 10. 阅读模式下没有右键入口 ✅
Obsidian 只对编辑模式发 `editor-menu`，而同步笔记默认以阅读模式打开，等于日常那条路上根本没有菜单。
新增 `ui/context-menu.ts`：各 feature 把菜单项注册到同一个注册表，编辑模式走官方事件，
阅读模式自己监听预览区 `contextmenu` 再弹 `Menu`（不是 Puzle 笔记就原样放行，不抢系统菜单）。
菜单弹出时抓选区快照传给贡献者 —— 点菜单项会让 DOM 选区消失，不能等到点击时再取。
「AI 续写」只在编辑模式出现：它要往光标处插字，阅读模式无处可插。

### 11. 创建高亮后要等下次同步才看得见 ✅
`==高亮==` 是同步渲染 managed 区时注入的，写回只是 POST + 刷新侧边栏，笔记纹丝不动。
新增 `sync/article-refresh.ts`：写回成功后就地重建这一篇 —— 复用 ArticleSyncer 的
`fetchArticlePayload` + `writeArticleNote` + `HighlightSyncer`，不另起一套渲染路径。
代价是 4 个请求（detail / summary / highlights / comments）。
顺带在 `syncState.articles[id]` 记下 `resourceType`，刷新时才知道调 link 还是 file 详情接口。

### 12. 下线 AI 续写 ✅
决策：**拿掉**。理由：与「把阅读资产同步进 Obsidian」这条主线无关，是唯一一个在非 Puzle 笔记上生效的功能，
还占着一个隐藏会话（`continuationChatId`）和散落在会话列表 / ChatSyncer 里的排除逻辑。
删掉 `src/writer/`、`tests/writer/`、状态栏项、`continueMaxChars` 设置项与两条 e2e 用例。
`syncState.continuationChatId` 字段保留（只读）：老账号里那个专用会话仍要挡在会话列表与对话同步之外，
否则它会突然冒出来变成一篇满是「请直接续写以下文字…」的对话笔记。

### 13. 批注面板太挤 + 缺删除入口 ✅
密度问题出在「每条高亮都是一个带框卡片，框内还套一条引用竖线，动作按钮是常驻的灰色胶囊」——
7 条高亮就是 7 个方块 + 14 个按钮。改法：
- 卡片去掉外框与底色，只留左侧一道 2px 竖线做归属（用户划的用强调色，AI 划的用弱色），条目之间靠留白分隔；
- 条目间距、行高、区块间距整体放大（`--size-4-5` / 1.65），想法块给一层浅底色与正文拉开层次；
- 动作按钮常态压到 45% 透明度，指到哪条才亮哪条；
- 「发表」按钮只在输入框里有字时出现，省掉常驻的一整行；
- 分类标签为空时不再渲染一个空胶囊（后端不返回 category 时的实际观感）。

删除入口：高亮与单条想法都可删，两步确认（点一下变「删除高亮？」再点才真删），删完立刻重建这篇笔记。

关于「AI 创建的高亮/评论能不能删」：查了两个 Web 客户端 —— 新版 `puzle-read-web` 的删除按钮**不按 role 拦**，
老版 `puzle-read` 只拦 `hidden` 标注（注释原话：「hidden 的 AI 标注不应有任何交互」），而 `hidden` 的高亮插件本来就不展示。
所以前端层面没有「AI 的删不掉」这条规则；后端是否另有限制，只能实删一次才知道，故实现上不做前端拦截，
拒绝时把服务端原话透出来。

## 实机联调发现并修掉的问题（2026-08-18，CDP 连真实 Obsidian）

1. **批注面板打开就空白** —— 面板用 `getActiveViewOfType(MarkdownView)` 判断当前文章，
   而打开侧边栏视图本身会夺走焦点，`active-leaf-change` 随即把文章置空。
   改用 `workspace.getActiveFile()`（焦点在侧边栏时它仍指向那篇笔记），
   并抽出 `ui/leaf.ts#getActiveMarkdownView` 做回退查找。
2. **重启后面板空白** —— 布局恢复时视图先于任何 `file-open` 挂载，事件永远等不到。
   视图 `onOpen` 主动对齐一次 + `onLayoutReady` 补一次。
3. **从高亮笔记点进去面板变空** —— 高亮笔记也该显示所属文章的批注，
   按 frontmatter 的 `reading_id` 经同步状态回溯到文章。

### 联调结论

- **高亮定位口径校准：`raw` 口径 35/35（100%）精确还原**（采样 5 篇真实文章）。
  其余三种候选均为 2/35。反向映射的地基已被真实数据证实。
- 划词创建高亮空跑（拦截 POST）：阅读模式选区 → `start_index/end_index` → `content`
  与选中文字完全一致。
- 文章级评论、单条高亮回复、「就这段提问」、会话列表、
  「与本文对话」复用既有 chat_id：均已在真实账号上验证，无 console 报错。
  （当时一并验证过的主区域聊天页与左边栏会话列表，已按第二轮决策删除。）
